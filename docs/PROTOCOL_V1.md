# Foundation protocol v1

The app uses typed XPC messages to the coordinator. Ordinary JSON-encoded replies have a 2 MiB client cap. Full static-analysis replies are a separately bounded bulk class with a 12 MiB client cap because the modern analysis report contains dozens of independently bounded evidence sections. Snapshots remain transactionally limited to 1,500,000 encoded bytes. Up to 100 records and 4096 UTF-8 bytes per note are supported.

Header worker requests use a fixed executable plus argument array: `reworker --inspect-header ABSOLUTE_PATH REQUEST_UUID`. No shell command is constructed. This is a narrow launch contract; the general framed request/handshake protocol remains future work.

The worker returns exactly one big-endian 32-bit-length-prefixed UTF-8 JSON response. Header/capture/page/control frames remain capped at 256 KiB. Static-analysis results use a distinct 8 MiB frame ceiling; no other operation inherits that larger budget. Header success fields are protocol=1, request_id, kind=header_result, file_kind, architecture, decimal-string size, header_hex, captured=false. An error uses protocol=1, kind=error and message. The coordinator validates success fields, identity, version, size and coverage, and rejects extra frames/output.

Inspection reads at most 32 source bytes and checks file length/mtime around the read. This is not immutable capture and cannot prove the entire source remained unchanged. Type labels based on magic bytes are candidates, not structural Mach-O validation.

Only one worker is active per coordinator connection. It obtains a 128 MiB reservation from the Rust admission model; actual resident memory is not polled in this increment. Worker deadline is 120 seconds, then terminate and an additional half-second before SIGKILL if still running. Lease revocation happens before cancellation completion; a cancelled result cannot be inserted. stdout, stderr and process termination are joined asynchronously; CoordinatorService does not block a user-initiated thread in `waitUntilExit()` or `DispatchGroup.wait()`. A process that has not exited retains the supervisor slot until the asynchronous lifecycle join completes.

Each connection owns its project state. Disconnect cancels work and releases the project when its outstanding callback finishes. A writer lock excludes a second project writer. Heavy Rust worker admission is serialized across independent HindSight instances with a per-user nonblocking file lock in addition to the in-process lease governor. A second forced app instance receives a bounded busy error instead of starting another analysis worker.


## v0.3 capture extension

The app's existing `inspectHeader` XPC entry now requests capture and inspection. Worker CLI: `--capture-inspect SOURCE STAGING REQUEST_UUID`. Staging is generated by the project coordinator, not supplied by an external script through XPC. Legacy `--inspect-header` remains for fixtures and emits an uncaptured observation.

Capture results retain protocol 1 / kind `header_result` and add `source_sha256` (64 lowercase hexadecimal characters), `structure_status` (`checked`, `unsupported`, `rejected`) and `structure` (bounded textual report), with `captured: true`. Before persisting, the coordinator adds `object_name`, a relative path under `objects/`. These four fields are optional when decoding legacy stored records. The capture supervisor requires the exact capture response field set; object_name is never trusted from a worker. Frames remain big-endian 4-byte lengths with a 256 KiB supervisor limit.

`checked` means only documented structural checks succeeded, not a validated executable. Size and addresses are string/text representations to avoid JSON floating-point loss. A successful capture can carry a rejected layout; capture failures produce an error and no record. Worker timeout: 120 seconds; client timeout: 150 seconds.

Layout constants follow Apple’s Mach-O loader definitions: https://github.com/apple-oss-distributions/xnu/blob/main/EXTERNAL_HEADERS/mach-o/loader.h and LLVM https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/BinaryFormat/MachO.h . This parser implements only the subset described above.


## v0.4 preview extension

Capture responses also require `disassembly_status` (`preview` or `unavailable`) and `disassembly` (UTF-8 text under 64 KiB). Both fields decode optionally in old persisted records. The supervisor validates the exact new capture field set and both report budgets; general frame limits remain unchanged.

`preview` means a limited linear decoding of at most 256 words from a single checked executable `__text` mapping. It does not establish instruction coverage, function boundaries or semantics. `unavailable` carries the mapping/format refusal reason. Source capture can succeed independently of preview availability. Branch destinations are unslid image addresses; they are never process pointers.


## v0.5 on-demand page request

XPC: `instructionPage(recordID, startWord, requestID, reply)`. The record ID must identify a captured object in the open project. The service validates `objects/<sha256>-<UUID>.bin`, resolves it itself and sends the bundled worker `--page PATH SHA256 SIZE START_WORD REQUEST_UUID`. Clients cannot supply arbitrary object paths through this endpoint.

Worker result: protocol 1, kind `page_result`, matching request_id/source_sha256, decimal-string start_word/total_words/section_address/section_offset, integer word_count (1–256) and text under 64 KiB. The supervisor requires exactly these fields, valid extents and the expected final-page count. The service wraps it as `{ok, message, page}`. Failure produces no page and no database changes.

The same one-worker admission, 256 KiB frame limit, cancellation/reaping and 120-second worker / 150-second client deadlines apply. Record selection generations suppress stale UI results. Page requests rehash the source without consuming its descriptor cursor, then inspect/read the same descriptor. This does not create an atomic snapshot against hostile concurrent writes.


## v0.6 cache control

The bundled XPC page method adds `forceVerify: Bool`. False permits metadata-keyed reuse; true clears the connection's cache and forces the hashing worker. The app and service must be updated together. Worker `--page` frames remain unchanged and always represent fresh verification.

A cached page is rebound to the current request_id. PageReply.message explicitly distinguishes cached metadata continuity from full SHA-256 verification. The coordinator checks current object references and metadata even on cache hits, and refuses requests while a worker is active. Immediate cache hits need no worker lease and complete synchronously on the service queue; subsequent cancellation may report already finished.


## v0.7 decoder revision

Frame shapes and pagination limits are unchanged. Newly generated report text identifies A64 subset v2. Coordinator cache keys use `page-cache-v2-a64-integer`; historical persisted preview strings are not migrated. Capability `integer_memory_decode: true` means the documented subset, not complete A64 coverage or execution support.


## v0.4.0-beta.5 analysis lifecycle repair

`--analyze` returns `kind=analysis_result` with the complete `AnalysisReport` field set defined in `Shared/WorkbenchMessages.swift`. The Swift field whitelist and Rust worker format are validated for exact parity during source validation; adding or removing an analysis field on only one side is a release failure.

Analysis is the only worker operation permitted to exceed the 256 KiB control-frame ceiling. Its worker frame is capped at 8 MiB and the enclosing XPC reply at 12 MiB. Each decoded textual evidence section remains independently bounded by `AnalysisReport.matches`. The larger cap is not a general-purpose message-size increase.

CoordinatorService drains worker stdout and stderr concurrently on utility queues and observes process exit through `Process.terminationHandler`. Final publication runs on the coordinator serial queue after all three asynchronous lifecycle events complete. This avoids the beta.4 priority inversion in which a user-initiated thread synchronously waited on lower-QoS worker plumbing.


## v0.4.0-beta.6 analysis status and deadlines

`inspectionStatus(requestID, reply)` exposes a bounded observation of the active or recently completed worker request. Analysis uses the phases `admitted`, `launching`, `running`, `receiving`, `validating`, `publishing`, `cancelling`, `completed`, `failed`, and `cancelled`. Status records contain the operation name, bounded diagnostic text, millisecond timestamps, and elapsed duration. The supervisor retains only the 32 most recent terminal/request states; this is diagnostic state, not a durable project record.

Analysis uses a 240-second worker deadline and a 260-second client request deadline. Capture/page requests keep the existing 120-second worker and 150-second client envelopes. A status-poll timeout is non-fatal and does not invalidate the XPC generation; the primary analysis request remains authoritative. Cancellation revokes publication permission before process termination and transitions through `cancelling` to `cancelled` only after the worker lifecycle has joined.


## v0.4.0-beta.7 Mach-O admission semantics

`LC_FUNCTION_STARTS` (`0x26`) and `LC_DATA_IN_CODE` (`0x29`) are normal Mach-O analysis metadata and never reject an otherwise valid ARM64 `__text` mapping. Data-in-code ranges are propagated to the worker as bounded decode barriers so those bytes are not promoted as instructions, CFG edges, or SSA facts. A nonzero `cryptid` in `LC_ENCRYPTION_INFO(_64)` yields a valid mapped-but-encrypted state: preview pages are unavailable, while metadata/linkage/string/runtime analysis may still proceed. No ciphertext is represented as decoded code.


## v0.4.0-beta.9 Coordinator handshake and project rehydration

A successful XPC connection is not sufficient to declare an analysis session ready. The app first decodes the `capabilities` response and requires the exact product version, release channel, ABI 1, Rust bridge, analysis, and execution capability set expected by the running app. A plain-text bridge failure, malformed JSON, version mismatch, ABI mismatch, or missing required capability keeps the Coordinator unavailable to the workbench.

After interruption/invalidation, the client abandons the old XPC generation and establishes a fresh connection. If the app still has a project snapshot, the new Coordinator process is considered transport-online but **project-session unavailable** until `openProject(path, create:false)` succeeds. Project-bound actions remain disabled during this window. A successful restore refreshes the project snapshot while preserving client-side drafts and selection where the selected record still exists. A failed restore leaves the Coordinator reachable but the project session unavailable, with an explicit retry path.

This recovery contract is advertised through `coordinator_handshake_validation`, `coordinator_session_rehydration`, and `beta_diagnostics`. The diagnostics surface reports product/service identity and bounded session state but intentionally reports only the project basename, not its full filesystem path.



## v0.4.0-beta.10 launch/session continuity

Launch continuity is an app-side recovery layer above the existing Coordinator protocol; it does not introduce a new XPC method or make local preferences authoritative for project state. The persisted record is limited to schema version, absolute project path, optional selected record ID, workspace, layout preset, and update timestamp. The app accepts it only when its encoded form is bounded and the workspace/layout values belong to the current catalogs.

After a fresh `capabilities` handshake, HindSight may call the existing `openProject(path, create:false)` using that saved path. Only a successful service reply may repopulate the project snapshot and unlock project-bound actions. Selection/workspace/layout restoration occurs after that reply. A path that no longer resolves locally is discarded and normal project creation/opening remains available. A service-side project validation failure is surfaced and remains explicitly retryable/forgettable.

The bridge advertises `launch_session_continuity`, `automatic_last_project_reopen`, and `stale_launch_session_recovery`. No unsaved note body, debugger state, runtime memory, or analysis report is serialized by this launch-continuity record.

## v0.4.0-beta.11 responsive-workbench capability metadata

The responsive-workbench re-architecture does **not** add or change an XPC method, request payload, response payload, or binary protocol field. Protocol ABI remains **1**. The app and Coordinator still require the exact product-version/release-channel handshake, so both sides now identify as `0.4.0-beta.11`; a mixed beta.10/beta.11 pair remains intentionally incompatible even though the transport schema itself is unchanged.

The bridge capability document now advertises `adaptive_workspace_topology`, `responsive_workbench_chrome`, and `overflow_safe_metric_bands`. These flags describe app/workbench presentation guarantees and release compatibility; they are not service action endpoints and do not grant additional Coordinator authority. Project-session readiness, launch-session rehydration, analysis admission, cancellation, and publication semantics remain unchanged from the beta.9/beta.10 contracts above.



## v0.4.0-beta.12 analysis synthesis fields

Protocol ABI remains **1** and no XPC method is added. The release-matched `analysis_result` exact-field schema is now **66 fields**. Beta.12 added `function_intelligence`, `data_references`, and `analysis_insights`; beta.14 adds `tail_call_candidates`, `function_neighborhoods`, and `analysis_quality`. Every added evidence section is limited to less than 64 KiB by `AnalysisReport.matches`, and Swift/Rust exact-field parity remains a release gate.

`function_intelligence` contains transparent structural triage facts and a disclosed attention formula; its score is not a semantic/security verdict. `data_references` contains only architecturally explicit PC-relative sites whose final target validates against a parsed Mach-O section, with adjacent-only ADRP+ADD promotion. `analysis_insights` summarizes those evidence classes without adding new facts.

The bridge advertises `function_intelligence`, `pc_relative_data_references`, and `analysis_insights`. Exact product-version handshake compatibility means beta.12 app/service/worker components must be deployed together.

## v0.4.2 staged analysis status and cache envelope v2

Protocol ABI remains **1** and `analysis_result` remains the exact 66-field report. `inspectionStatus` now includes bounded `progress_percent` and `progress_stage` fields and the `checkingCache` phase. These fields describe execution state only; they do not make a partial analysis report authoritative.

The worker's final result remains length-framed on stdout. During analysis only, stderr may carry strict `VG_PROGRESS` records that Coordinator consumes into `InspectionStatus`; accepted progress records are removed from diagnostic stderr. Cache envelope schema 2 binds cached reports to an explicit analysis-engine identity and producer version. 0.4.2 explicitly admits the compatible 0.4.1 schema-1 cache and migrates it after ordinary report/source validation.

## v0.4.1 stable identity and project-local analysis reuse

Protocol ABI remains **1** and the `analysis_result` transport remains the exact 66-field beta.14 schema. App/Coordinator capability handshake identity is now product version `0.4.1` with release channel `stable`; mixed beta/stable binaries are intentionally rejected.

Project-local analysis caching does not add an XPC method or field. CoordinatorService may satisfy an existing `analyzeRecord` request from a bounded cache only when the captured SHA-256 and exact product version match. Before returning a cached report, Coordinator revalidates the cache envelope/report and rebinds only the request UUID; source identity and evidence payload remain unchanged. Cache miss/failure falls through to the ordinary isolated worker path.
